# EPIC-14 implementation architecture: Extension points (first-party contributions + text filters)

Baseline `master` SHA: `bbfb010074fbe44201ab6a8b1c4d6244c51ecf18` (merge of #52,
2026-09-02). Product contract: GitHub issue #15. A documentation-only commit
(`0987c99`, marking E13 done in `planning/epics/README.md`) sits on top of
this baseline on the working branch; it is pre-epic housekeeping, not part of
E14.

---

## 1. Owner summary

**What changes for the user?** Two independent things, both under the hood
until the user reaches for them.

First, MacDown 2 gains its first piece of Markdown content that is
*generated*, not typed. Typing a line containing only `[TOC]` and saving
turns that line, in Preview and in every export, into a table of contents
built from the document's own headings — indented by heading level, kept in
sync every time a heading changes. The `[TOC]` line itself is never removed
from the file; only the *rendered* preview and export show the generated
list.

Second, power users get a small local automation system: drop an executable
script into a `Commands` folder inside the app's own Application Support
directory, and it appears in a new **Commands** menu and in a searchable
command palette (`⌘⇧P`). Running it sends the current selection (or, with no
selection, the whole document) to the script's standard input and replaces
that same text with whatever the script prints to standard output — a fast,
scriptable way to do things MacDown 2 will never build a dedicated UI for
(sorting lines, reformatting a table, wrapping text a particular way).
Nothing runs unless the user put the script there themselves, and a script
that fails, hangs, or misbehaves leaves the document exactly as it was.

**Why now?** `planning/epics/README.md`'s sequencing places E14 immediately
after `formats/export/settings` (E11/E12/E13, all now done) and before E19
(math) and E20 (diagrams + Mermaid). Both of those epics need a place to put
"a block of the document is generated by a renderer, not authored by hand,"
and the issue is explicit that this must be **one** mechanism, not a
preview-specific one that export has to reinvent. Building that mechanism
now, proven by one concrete, low-risk feature (TOC) and one deterministic
test double, is materially cheaper than discovering the right shape for it
under the added pressure of a real KaTeX or Mermaid integration.

**Main technical approach, in plain language.** A contribution is a small
piece of first-party Swift code that looks at a parsed document and
optionally says "replace this exact range of the source with this piece of
generated content." That statement — the range, the content, and whether it
succeeded — is the *only* thing a contribution produces. It is not a SwiftUI
view and it does not know whether it is feeding Preview or an HTML/PDF
export. Preview and Export each already have a real place to receive
externally-supplied content: Preview's block renderer already accepts a
pre-computed list of blocks instead of computing its own, and Export's
`ExportRequest` already has an (currently always-empty) `contributions`
array that E12 built and wired all the way through its HTML/PDF pipeline
without ever populating it. This epic is what finally populates both. A
small, new "adapter" at the app layer turns one contribution's generic
result into the specific shape each destination already knows how to
consume — no change to `Preview`'s or `ExportService`'s existing public
surface beyond one small, additive export-side function (§5, §6).

Text filters are architecturally unrelated to contributions — they replace
selected text via an external process, not document content via a renderer
— and are built as a second, independent module with its own, much
stricter trust boundary (§10): every process launch uses structured
arguments only, runs off the main actor, is bounded in time and output, and
the app is unsandboxed today (D7), so the *script itself* is exactly as
trusted as anything else the user could run from Terminal — MacDown 2's own
obligation is narrower: never turn document text into shell syntax, always
bound what it waits for, and never touch the editor except with a script's
successful, complete output.

**Main risks or compromises.**

1. A contribution's derived content in this epic is always expressible as
   Markdown text (a list of links, for TOC). A future contribution whose
   output cannot be expressed as Markdown — a rendered equation image, an
   SVG diagram — does not fit that shape. Rather than guess at that shape
   now, the result type carries an explicit `.html(String)` case alongside
   `.markdown(String)` that **no adapter in this epic handles** (§6, §18).
   E19/E20 will get a compiler error, not a silent gap, the day they need
   it — but they will also inherit a real, currently-unsolved problem:
   Preview's block renderer has no HTML-fragment rendering capability at
   all today (§18).
2. Export computes contributions by parsing the document a second time,
   independently of the parse `ExportComposer` already performs internally
   (§7, §11). This duplicates a parse that is already known to be cheap
   (E06's own budget) and avoids the alternative of threading Preview's
   live parse session into `ExportCoordinator`, which would couple two
   parts of the app that have been fully independent since E07/E12 shipped.
3. Text-filter commands are local automation, not a security sandbox. This
   epic's safety contract governs how MacDown 2 *launches* a script
   (§10) — it does not restrict what an already-launched script can do on
   the user's Mac. That is consistent with D7 (unsandboxed, direct
   distribution) and with the issue's own framing ("a simple local
   text-filter command system"), not a gap introduced by this epic.
4. The command palette's "app commands" list is a small, explicitly
   hand-written array, not a general command-registration framework every
   future menu action must register through (§5). Building the general
   version is explicitly not justified by this epic's actual requirement.

**What is deliberately not being built.**

- Any math or diagram rendering (E19/E20/E21 own that entirely; this epic
  ships no contribution other than TOC and the deterministic test double).
- HTML-fragment rendering inside Preview (§18 — a named, open gap for
  E19/E20, not solved here).
- A third-party extension loader of any kind, JavaScriptCore or otherwise
  — only a design document for a possible post-1.0 API (§17, Slice 8).
  Nothing this epic ships executes third-party code.
- Reintroducing NSBundle/dylib in-process plugin loading (D6 — retired
  permanently).
- A sandboxed or otherwise restricted execution environment for text-filter
  scripts. They run with the same OS-level privileges any process the user
  launches has; see risk 3 above.
- Auto-installing example scripts into the user's real Commands folder on
  launch. Examples ship as read-only app resources; a user-initiated action
  copies them out (§9, §17 Slice 6) — nothing writes to
  `~/Library/Application Support` before the user asks for it.
- A generic, extensible command-registration system for the palette (risk 4
  above).

## 2. Baseline and repository reconciliation

### 2.1 What already exists and must be reused, not duplicated

**E12's contribution seam is real, built, tested, and completely unused.**
`ExportDerivedContribution` (`Sources/ExportService/ExportDerivedContribution.swift`)
already has exactly the shape a renderer-neutral export contribution needs —
a UTF-16 `sourceRange` into the *original* source, `placement`
(`.inline`/`.block`), a self-contained `html` fragment, a `sourceGeneration`
for staleness rejection, and `[ExportDiagnostic]`. Its doc comment says, verbatim:
"E14/E19/E20 later supply instances of this type; E12 never calls a math or
diagram renderer." `DerivedContentComposer` (same directory) already knows
how to splice zero or more of these into a document's body before cmark-gfm
renders it, and already rejects — without failing the export — a
contribution that is stale, out of the source generation, out of range,
overlapping another contribution, or empty, replacing it with the original
authored text and recording an error diagnostic either way. `ExportRequest`
(`ExportRequest.swift`) already carries `public let contributions:
[ExportDerivedContribution]` with a default of `[]`. Grepping the module
confirms there is exactly one production construction site for
`ExportRequest` — `MacDown2/ExportCoordinator.swift:182` — and it does not
pass `contributions:` today. None of this is prototype code behind a flag;
it is fully unit-tested, shipped, dead-until-populated infrastructure. This
epic's Export adapter (§7, Slice 4) populates it; it changes nothing about
`ExportDerivedContribution` or `DerivedContentComposer` themselves.

**Preview's block renderer already accepts externally-supplied blocks.**
`TextualMarkdownPreview` (`Sources/Preview/TextualMarkdownPreview.swift`)
has `public let blocks: [PreviewBlock]?` — "pre-computed preview blocks, if
the caller caches them. When `nil` (the default) blocks are sliced lazily
from `document`/`text`." The app target already exercises the *caller*
side of this today: `MacDown2/DocumentEditorSplitView.swift` computes
`previewBlocks = PreviewBlock.blocks(from: document, text: text)` itself
(in `refreshPreviewBlocks()`, called from both `.task(id: identity)` at
initial load and `.onChange(of: parseSession.document)` on every reparse)
and hands the result to `TextualMarkdownPreview(blocks: previewBlocks,
...)`. This means the Preview adapter (§7, Slice 3) has zero work to do
inside the `Preview` module — it only needs to change what
`DocumentEditorSplitView` builds *before* handing `previewBlocks` off,
by splicing in one synthetic `PreviewBlock` per placed contribution.
`PreviewBlock`'s own `kind: BlockKind` already has a `case custom(String)`
described in its doc comment as "the totality escape hatch" — precisely
built for content that does not correspond to a block cmark actually
parsed. `PreviewBlock.source` is always Markdown-shaped text (fed straight
into `PreviewMarkupParser`/Textual downstream in `BlockView`), never HTML —
confirmed by reading `PreviewBlock.swift` directly, not inferred. This is
the deciding fact behind the `.markdown`-only scope of this epic's adapters
(§18).

**`HeadingItem`/`MarkdownDocument.headings` is already exactly TOC's input.**
`Sources/MarkdownEngine/MarkdownBlock.swift` defines `public struct
HeadingItem: Sendable, Equatable { level: Int; title: String; lineRange:
ClosedRange<Int> }` with `title` already the plain-text inline content,
markup stripped. `MarkdownDocument` (`MarkdownDocument.swift`) exposes
`public let headings: [HeadingItem]` with the doc comment "All headings in
document order (flattened from `blocks`)." No new parsing or tree-walking
is needed for TOC's data source — it already exists, already flattened,
already ordered.

**`SourceMap` is the existing, only line ↔ UTF-16 bridge.**
`Sources/MarkdownEngine/SourceMap.swift`'s `utf16Range(ofLines:) ->
NSRange` and `line(atUTF16Offset:) -> Int` are what
`PreviewBlock.blocks(from:text:)` already uses to turn a block's 1-based
`lineRange` into the UTF-16 range of its source text, and what this epic's
TOC contribution and Preview adapter reuse for the same purpose (§6, §7).

**Export already parses independently of Preview, today, before this
epic.** `ExportComposer.prepare` (`Sources/ExportService/ExportComposer.swift`)
performs its own `engine.parse(request.text, options: .default, revision:)`
call, fully independent of whatever `MarkdownParseSession` inside
`DocumentEditorSplitView` is doing for Preview at the same moment. There is
no existing precedent, and no existing plumbing, for Export to reuse
Preview's live parse — Export re-parses the frozen `ExportRequest.text`
snapshot from scratch every time, as it already does for the base
document body. This is the direct precedent for §7/§11's decision that the
Export contribution adapter performs its own extra, independent parse too,
rather than threading a per-tab contribution cache from Preview's session
into `ExportCoordinator`.

**No public "render this Markdown fragment to HTML" entry point exists
yet.** `ExportComposer` (internal, not `public`) is the only thing that
calls `CMarkGFM.render(...)`; the App target can only reach the module's
two `public` entry points, `ExportService.prepare`/`.exportHTML`, both of
which compose a *complete* document, not an arbitrary fragment. The Export
contribution adapter needs to turn a contribution's `.markdown(String)`
into `html: String` for `ExportDerivedContribution`, and no existing API
does that. §5/§6 add one small, new `public` function to `ExportService`
for exactly this — the one non-App-target source change this epic makes
outside its two new modules.

**The undo-as-one-edit idiom is already established and is reused, not
reinvented.** `Sources/EditorCore/EditorTextSystem+EditingAssists.swift`'s
`applyAssistOutcome(_:)` wraps a replacement in
`textView.breakUndoCoalescing()` → `textView.insertText(_:replacementRange:)`
→ `textView.breakUndoCoalescing()`, with no manual `registerUndo` call
anywhere — AppKit's own `insertText(_:replacementRange:)` registers the
inverse edit. A successful text-filter replacement (§9, Slice 6) applies
through this exact same idiom, at the same layer, not a new one.

**The cancel-on-supersede idiom already used for parsing is `Task.isCancelled`
+ a monotonic generation counter** (`MarkdownParseSession.textDidChange`,
`Sources/MarkdownEngine/MarkdownParseSession.swift`). SwiftUI's `.task(id:)`
modifier is the declarative form of the same idea (a new `id` cancels the
previous task automatically) and is already used elsewhere in the app target
(the font-reapplication task in `WorkspaceShellView.swift`). The Preview
contribution adapter (§8, Slice 3) uses `.task(id:)`, not a hand-rolled
generation counter, because nothing about running contributions needs
anything `.task(id:)` does not already give it for free.

**The `PDFExportAdapter`'s watchdog-vs-continuation timeout pattern**
(`MacDown2/PDFExportAdapter.swift`'s `PDFNavigationDelegate.load(_:in:timeout:)`)
is the direct template for bounding a text-filter command's execution time
(§10, Slice 5): a `Task` racing `Task.sleep(for:)` against the real
completion, guaranteeing the awaited call always returns (or throws)
instead of ever hanging indefinitely.

**The `"MacDown 2/<subdirectory>"` Application Support convention** is
already used identically in two places — `RecoveryBuffer.swift`
(`"MacDown 2/Recovery"`) and `WorkspaceSession.swift` (`"MacDown 2"`).
The Commands folder (§10, Slice 5) uses the same convention:
`"MacDown 2/Commands"`.

**Registry pattern precedent.** Two existing registries were read in full
to choose the right shape for `ContributionRegistry` (§6): `GrammarRegistry`
(`Sources/Highlighting/GrammarRegistry.swift`) is a `@MainActor` shell over
a `nonisolated`, lock-guarded cache, justified by tree-sitter grammar
*compilation* being expensive and needing cross-thread reuse.
`FileFormatRegistry` (`Sources/FileCore/FileFormat.swift`) is a plain
`Sendable` value holding a static array of value literals, with no
lazy-build step and no lock, because format metadata is just data.
Contributions are Swift value/struct instances, not a compiled artifact —
there is nothing to lazily build or cache — so `ContributionRegistry`
follows `FileFormatRegistry`'s shape, not `GrammarRegistry`'s (§6).

**Zero precedent for launching a subprocess anywhere in this repository.**
Confirmed by grep (`Process(`, `NSTask`) across the whole tree: no matches.
This epic is the first to add one. `RELEASE_HARDENING.md` §3's nine-bullet
text-filter safety baseline (quoted in full in §10) is the only existing
authority on how that must be done; there is no existing app code to
reconcile it against.

**Confirmed unsandboxed (D7).** No `.entitlements` file exists anywhere in
the repository (`find . -iname "*.entitlements"` is empty) and
`MacDown2/project.yml` declares no sandbox or hardened-runtime keys. A
`Process()` launch faces no OS-level sandbox barrier. This is the basis for
§1 risk 3 and §10's trust-boundary framing.

**`WorkspaceCommands.swift`'s `CommandMenu` precedent.** `CommandMenu("Folder")`
(line 84) is the existing pattern for a custom top-level menu; a new
`CommandMenu("Commands")` (§9, Slice 6) follows it exactly. `⌘⇧P` is
confirmed unbound anywhere in `WorkspaceCommands.swift`, and no "palette"
concept exists anywhere in the app today.

### 2.2 Stale assumptions reconciled

- **Issue #15's "registry/lifecycle/isolation model"** is written broadly
  enough to suggest something like `GrammarRegistry`'s cross-thread-cache
  complexity. Given contributions are cheap, synchronous-to-construct Swift
  values with no compiled-artifact cache to manage, this epic reconciles
  "isolation" as **fault and result isolation** (one contribution's failure
  or staleness cannot affect another's result, and never touches authored
  source) rather than OS-level process isolation, which is reserved
  entirely for the text-filter half of this epic, the only half that
  launches unsandboxed external code (§10 makes this split explicit, since
  the issue does not itself distinguish the two).
- **"Derived representation/capability metadata"** is reconciled as the
  `ContributionRepresentation` enum itself (§6) — its cases *are* the
  capability signal a consumer switches on — rather than a second,
  separate metadata field describing the same information redundantly.
- **Deliverable 5 ("clear handoff requirements for E19/E20")** is
  reconciled as a named, concrete, compiler-enforced gap (the unhandled
  `.html` case, §18) rather than prose promising a future epic will "figure
  it out" — the strongest form of handoff available without speculatively
  building HTML-fragment rendering this epic has no real user of yet.

### 2.3 Dependencies and follow-ups this epic intersects

- No open bug-tracker issue references E14 directly.
- `RELEASE_HARDENING.md` §2's "shared derived-content architecture" diagram
  and §3's text-filter safety baseline are the two binding, cross-epic
  constraints this epic exists to satisfy; both are reconciled throughout
  (§4, §10, §17).
- E19 (issue #44) and E20 (issue #45) both list E14 as a dependency and are
  still `open`; this epic's job toward them is entirely the handoff in §18,
  not any part of their own scope.

## 3. User journeys

**J1 — Write `[TOC]`, see a live table of contents.** The user is writing a
long Markdown document with several headings. They type `[TOC]` on its own
line and keep writing. In Preview, that line renders as an indented list of
links, one per heading, without the user doing anything else. They add a
new `## Section` heading above the `[TOC]` line; the list updates on the
next reparse, same as any other live preview content. The saved file on
disk still contains the literal text `[TOC]` — nothing rewrites the source.

**J2 — Export a document containing `[TOC]`.** The user exports the same
document to self-contained HTML. The exported file's table of contents
matches what Preview showed, built from the same headings, nested the same
way — not a picture of the preview, not a second, differently-coded
implementation of "list the headings." The list entries are plain text in
this epic, not clickable links (§6.2, §13) — no part of the export
pipeline generates a stable `id` for a heading today, and inventing one
correctly (matching cmark-gfm's actual rendered output, not just this
epic's own assumption about it) is real, separable work this epic does not
attempt speculatively. §18 names this as explicit follow-up scope.

**J3 — `[TOC]` with no headings, or no `[TOC]` at all.** A document with a
`[TOC]` line but zero headings renders that line as an empty list rather
than leaving the literal text `[TOC]` visible (which would look like a bug,
not "nothing to list"). A document with no `[TOC]` line anywhere is
completely unaffected — TOC contributes nothing, Preview and Export behave
exactly as they did before this epic shipped.

**J4 — Uppercase a selection with a text filter.** The user selects a
paragraph, opens the command palette (`⌘⇧P`), types "upper," and picks
"Uppercase Selection" (a bundled example script they previously copied into
their Commands folder via the empty-state's "Add Example Scripts" button,
§9). The selection is replaced with its uppercased form as one `⌘Z`-undoable
edit. Running it again with nothing selected uppercases the whole document
instead, per the selection-or-whole-document contract (§9).

**J5 — A text-filter script fails.** The user runs a script that has a bug
and exits with a non-zero status. The editor's text is completely
unchanged — not partially replaced, not replaced with an error message —
and an alert names the script and explains what happened (non-zero exit,
with the script's own stderr if it printed one). The same holds if the
script cannot be launched at all (not executable, moved, deleted since the
palette was last opened), hangs past the timeout, or is cancelled by the
user before it finishes.

**J6 — Discover text filters for the first time.** A user who has never
used this feature opens the Commands menu and sees an empty menu with a
single "Show Commands Folder in Finder" item and a short description of the
convention (an executable file, `stdin` in, `stdout` out). They also see an
"Add Example Scripts" affordance (in the same menu or the palette's empty
state) that copies MacDown 2's bundled read-only examples into their real
Commands folder — nothing is copied there automatically before this click.

**J7 — Invoke an app command from the palette.** The user opens the palette
and types "export"; "Export…" (the same command already bound to `⌘⇧E`)
appears alongside any discovered text filters and can be invoked the same
way, disabled under the same conditions the `Export…` menu item already is
(no exportable active document, or an export already in flight).

## 4. Non-negotiable invariants

1. **A contribution never rewrites the saved document.** `FileDocument.text`
   is never touched by a contribution, in either Preview or Export — only
   the *rendered* presentation changes. The authored `[TOC]` line is
   exactly what gets saved, reopened, diffed in source control, and
   round-tripped, forever.
2. **A failing or stale contribution degrades only itself.** One
   contribution's failure, staleness, or an out-of-range result never
   prevents another contribution from placing its own result, never fails
   the whole Preview render, and — reusing E12's already-shipped guarantee
   verbatim — never fails the whole export (§2.1).
3. **Preview and Export consume the same contribution computation, not two
   independent renderer implementations.** Both call the same `Contributing`
   value's `run(...)`; only the adapter that turns its result into a
   `PreviewBlock` or an `ExportDerivedContribution` differs (§5, §7).
4. **Text-filter commands never run on the main actor.** `TextFilterRunner`
   is not `@MainActor`; the process launch, wait, and output capture happen
   off it, so a hung script cannot freeze the app (mirrors
   `RELEASE_HARDENING.md` §3).
5. **No shell interpolation, ever.** A text-filter command is launched with
   `Process.executableURL`/`.arguments` set to a fixed, structured value;
   no document text, file path, or user input is ever concatenated into a
   string later interpreted by a shell.
6. **A text-filter replacement is applied to the editor only after the
   command has fully succeeded** (zero exit, within the timeout, output
   within the size/decoding bounds). Every other outcome leaves the editor
   completely untouched — this falls out of sequencing (compute the
   replacement fully before touching the editor), not a rollback mechanism
   (§9).
7. **No new cross-module dependency inside `MacDownKit` beyond the two new
   modules' own, narrow dependencies.** `Contributions` depends only on
   `MarkdownEngine`; `TextFilters` depends only on `Foundation`; neither
   `Preview` nor `ExportService` gains a dependency on either new module,
   or on each other. Only the App target imports across all of them (§5).
8. **No third-party or dynamically-loaded code executes.** NSBundle/dylib
   plugin loading stays retired (D6); the JavaScriptCore extension API is
   a design document only (§17, Slice 8) and ships no loader.
9. **Offline/local only (D9).** Nothing this epic adds performs a network
   request. A text-filter script *could* reach the network once launched —
   that is the script's own unsandboxed privilege (§10), not something
   MacDown 2's own code does or grants beyond what any local process
   already has.
10. **Every `UserDefaults`/Application-Support read this epic adds is
    reachable the same way existing ones already are for UI-test
    isolation** — the Commands folder resolves via the same
    `FileManager.default.urls(for: .applicationSupportDirectory, ...)` +
    `"MacDown 2/..."` pattern `RecoveryBuffer`/`WorkspaceSession` already
    use (§2.1), so a future UI-test isolation pass has one convention to
    special-case, not several.

## 5. Ownership and dependency boundaries

**`Contributions`** (new SwiftPM library target) **owns:**

- `Contributing` (protocol), `ContributionResult`/`ContributionContent`/
  `ContributionRepresentation`/`ContributionDiagnostic` (renderer-neutral
  result types), `ContributionRegistry`.
- The two first-party contributions this epic ships: `TOCContribution` and
  `DeterministicTestContribution`.
- Dependency: `MarkdownEngine` only (for `MarkdownDocument`, `HeadingItem`,
  `SourceMap`). No dependency on `Preview`, `ExportService`, `AppKit`, or
  `SwiftUI` — this is the module-level enforcement of "not a SwiftUI
  preview view" from the issue's own architectural rule.

**`TextFilters`** (new SwiftPM library target) **owns:**

- `TextFilterCommand`, `TextFilterRunner`, `TextFilterRunner.Limits`,
  `TextFilterError`, and the Commands-directory scanner
  (`TextFilterCommandDiscovery`, name TBD at implementation, §17 Slice 5).
- Dependency: `Foundation` only. Deliberately **not** a dependency on
  `FileTree` (which already has a small `DirectoryReading` protocol +
  `FileSystemDirectoryReader` doing a similar-shaped directory scan): a
  Commands-folder scan is a different operation (filtering to executable
  regular files, no subdirectory recursion, no folder-browser UI state) and
  importing a folder-browser module into a process-launching module for a
  few lines of `FileManager` code would be a coupling this epic's actual
  requirement does not justify. `TextFilters` writes its own small scan
  routine instead, matching `DirectoryReading`'s shape as inspiration, not
  as a shared dependency (§5 rule 7).
- No dependency on `MarkdownEngine`, `Contributions`, `Preview`, or
  `ExportService` — text filters operate on plain selected/whole-document
  text, never on parsed document structure.

**`ExportService`** (existing module) **gains exactly one small addition:**

- `public static func renderMarkdownFragment(_ markdown: String) -> String`
  on `ExportService` (§6) — a standalone cmark-gfm render of a fragment,
  with no metadata resolution, theme, or resource pipeline attached. This
  is the one non-App-target, non-new-module source change in this epic.
  Nothing about `ExportRequest`, `ExportComposer`'s whole-document
  pipeline, `ExportDerivedContribution`, or `DerivedContentComposer`
  changes.

**`Preview`** (existing module) is **unmodified.** `TextualMarkdownPreview`'s
existing `blocks: [PreviewBlock]?` parameter is the entire seam this epic
needs (§2.1); there is nothing to add to the module itself.

**App target (`MacDown2/MacDown2`) owns:**

- `PreviewContributionAdapter` — turns `[ContributionResult]` into extra
  `PreviewBlock`s merged into `DocumentEditorSplitView`'s existing
  `previewBlocks` computation (§7, Slice 3).
- `ExportContributionAdapter` — turns `[ContributionResult]` into
  `[ExportDerivedContribution]`, calling the new
  `ExportService.renderMarkdownFragment` (§7, Slice 4).
- `ExportCoordinator`'s new pre-parse + contributions wiring (Slice 4).
- The Commands menu, command palette UI, and the editor-mutation call site
  for a successful text-filter replacement (Slices 6–7).
- Constructing `ContributionRegistry.standard` and a `TextFilterRunner`
  where needed; neither is a long-lived `@Observable` controller like
  `AppSettingsModel` — both are cheap, stateless-per-call values
  constructed where used, not threaded through the environment (§6).

No module in `MacDownKit` gains a new dependency on `Contributions` or
`TextFilters` except the App target — matching exactly how only the App
target depends on `AppSettings`, `Themes`, and `ExportService`
simultaneously today (epic-13-implementation.md §5's precedent, carried
forward unchanged).

**Deliberately not built as a general framework:** the command palette's
"app commands" are a small, explicit, hand-written array in the App target
(§9, Slice 7), not a new command-registration protocol every menu action
must adopt. `WorkspaceCommands.swift`'s existing `Commands` scene already
enumerates every real app action in one place; duplicating a subset of it
into a flat array for the palette is simpler and more honest about scope
than inventing a registry that only two features (Commands menu items,
palette rows) would ever populate.

## 6. Types and interfaces

### 6.1 `Contributions` module

```swift
// ContributionPlacement.swift — mirrors ExportDerivedPlacement exactly,
// independently defined so Contributions has no dependency on ExportService.
public enum ContributionPlacement: Sendable, Equatable {

// ContributionResult.swift
/// One contribution's answer for one document snapshot. `content == nil`
/// means this contribution found nothing to do (e.g. no `[TOC]` marker) —
/// callers skip it entirely — or that it failed after finding something to
/// do, in which case `diagnostics` explains why and `content`'s absence
/// means there is no range to place anything at (§2.2's fault-isolation
/// reconciliation).
public struct ContributionResult: Sendable, Equatable {
    public let contributionID: String
    public let content: ContributionContent?
    public let sourceGeneration: UInt
    public let diagnostics: [ContributionDiagnostic]
    public init(
        contributionID: String,
        content: ContributionContent?,
        sourceGeneration: UInt,
        diagnostics: [ContributionDiagnostic] = []
    ) {
        self.contributionID = contributionID
        self.content = content
        self.sourceGeneration = sourceGeneration
        self.diagnostics = diagnostics
    }
}

// Contributing.swift
/// A first-party contribution. Implementations are trusted, in-process
/// Swift — this protocol has no bearing on the text-filter trust boundary
/// (§10).
public protocol Contributing: Sendable {
    /// Stable, never user-facing (diagnostics/tests only), e.g. "toc".
    var id: String { get }

    /// Produces zero or more results for one document snapshot. Called
    /// fresh per caller (§7 — Preview and Export each call this
    /// independently, from their own parse); a contribution does not
    /// cache across calls. Cooperatively cancellable: long-running work
    /// must poll `Task.isCancelled` (mirrors `MarkdownParseSession`,
    /// §2.1). May throw for a genuinely unexpected failure — the registry
    /// (below) converts a thrown error into a diagnostic-bearing result
    /// with no `content`, isolating it from every other registered
    /// contribution's run.
    func run(
        document: MarkdownDocument,
        sourceText: String,
        sourceGeneration: UInt
    ) async throws -> [ContributionResult]
}

// ContributionRegistry.swift — FileFormatRegistry's shape (§2.1): a plain
// Sendable value over a static array, no lock, no lazy-build cache.
public struct ContributionRegistry: Sendable {
    public let contributions: [any Contributing]
    public init(contributions: [any Contributing]) {
        self.contributions = contributions
    }

    /// The first-party contributions MacDown 2 ships.
    public static let standard = ContributionRegistry(contributions: [TOCContribution()])

    /// Runs every registered contribution and aggregates results.
    /// Isolation: one contribution throwing does not prevent the rest from
    /// running, and is recorded as its own error diagnostic rather than
    /// silently dropped. Cancellation is the one exception — a thrown
    /// `CancellationError` propagates out of this call immediately,
    /// abandoning the remaining contributions, matching Swift's own
    /// structured-concurrency convention that cancellation is not "one
    /// more failure to report" (§8).
    public func run(
        document: MarkdownDocument,
        sourceText: String,
        sourceGeneration: UInt
    ) async throws -> [ContributionResult] {
        var results: [ContributionResult] = []
        for contribution in contributions {
            do {
                try Task.checkCancellation()
                let contributed = try await contribution.run(
                    document: document, sourceText: sourceText, sourceGeneration: sourceGeneration
                )
                results.append(contentsOf: contributed)
            } catch is CancellationError {
                throw CancellationError()
            } catch {
                results.append(ContributionResult(
                    contributionID: contribution.id,
                    content: nil,
                    sourceGeneration: sourceGeneration,
                    diagnostics: [ContributionDiagnostic(
                        severity: .error,
                        message: "\(contribution.id) failed: \(error.localizedDescription)"
                    )]
                ))
            }
        }
        return results
    }
}
```

## 8. Concurrency and cancellation

**Contributions (`Contributions` module + adapters).**
`ContributionRegistry.run` is `async`, not actor-isolated — it can be
awaited from any isolation domain, including the App target's
`@MainActor`-bound SwiftUI `.task(id:)` (Preview) or `ExportCoordinator`
(already `@MainActor`, §2.1, for Export). A `Contributing` implementation
that ever needs real background work (a future E19/E20 renderer) is free
to hop off the main actor internally; nothing in this epic's protocol
forces main-actor execution, matching `RELEASE_HARDENING.md`'s general
"expensive rendering does not block the main actor" invariant even though
TOC itself is cheap enough not to need it.

**Preview's cancellation is `.task(id: parseSession.document)`, not a
hand-rolled generation counter.** SwiftUI cancels and restarts this task
automatically whenever `parseSession.document` changes (it is `Equatable`,
§2.1), which is the exact moment any previously-computed
`contributionResults` are stale anyway. This is strictly simpler than
porting `MarkdownParseSession`'s manual `pendingTask?.cancel()` +
generation-counter idiom into the App target, because `.task(id:)` already
gives the same guarantee declaratively, and is the pattern already used
elsewhere in this app target (the font-reapplication task in
`WorkspaceShellView.swift`, §2.1) for the same reason.

**Export's contribution run is not independently cancellable beyond what
`exportActiveDocument()` already provides.** `ExportCoordinator
.exportActiveDocument()` is one `async` call from a `Task { }` started by
a menu action; cancelling that outer `Task` (there is no explicit "Cancel
Export" affordance today, matching pre-epic behavior) cancels everything
inside it, contribution running included, via ordinary structured
concurrency — no new cancellation surface is introduced.

**`ContributionRegistry.run`'s per-contribution isolation vs. cancellation**
is specified precisely in §6.1: a thrown `CancellationError` from one
contribution propagates out of the whole registry call immediately
(abandoning remaining contributions, matching Swift's own convention that
cancellation is not a recoverable per-item failure); any other thrown
error is caught, converted to a diagnostic-bearing result with no
`content`, and the loop continues — this is the concrete mechanism behind
§4 invariant 2's "one contribution's failure never prevents another's."

**Text filters run off the main actor by construction.** `TextFilterRunner`
carries no actor annotation and is `Sendable`; its `run(_:input:)` is
called from a plain background `Task` (or `Task.detached`) at the App
target's Commands/palette call site, never from a `@MainActor`-isolated
context directly awaiting the process. The one main-actor touch is the
editor mutation itself, which — like every other AppKit text mutation in
this app — must happen on the main actor, and happens strictly *after*
`TextFilterRunner.run` returns.

**Text-filter timeout and user cancellation both terminate the live
process.** Mirroring `PDFNavigationDelegate.load(_:in:timeout:)`
(§2.1) exactly: a watchdog `Task` races `Task.sleep(for: limits.timeout)`
against the process's real completion; on timeout it calls
`process.terminate()` and the call throws `.timedOut`. If the calling
`Task` is cancelled (e.g. the window closes mid-run — no explicit "Cancel"
button is in this epic's scope, §17 Slice 6), `TextFilterRunner` checks
`Task.isCancelled` at its await points and calls `process.terminate()`
before throwing `CancellationError`/`.cancelled` — a script is never left
running with no one waiting on it.

**What happens when the document changes while a text filter is
running.** The command was already handed a frozen `input: String`
snapshot (the selection or document text at the moment the command was
invoked) — a concurrent edit elsewhere is irrelevant to that snapshot.
When the command completes, the replacement is applied at the *same
range* the input was read from; if that range is no longer valid (the
user made an incompatible edit — e.g. deleted the selection — while the
script was running), the replacement is applied as a fresh insertion at
the nearest valid position (clamped, not rejected) rather than silently
dropped or crashing — this mirrors `EditorTextSystem`'s own existing
range-clamping behavior elsewhere, not a new invariant this epic invents.

## 9. Failure model

| Failure | Response |
|---|---|
| Document has a `[TOC]` marker but zero headings (J3) | TOC still replaces the marker, with an empty Markdown list — never leaves the literal `[TOC]` text on screen once a marker was found |
| Document has no `[TOC]` marker at all | `TOCContribution.run` returns `[]` — no diagnostic, this is not a failure |
| Document has multiple `[TOC]` markers | Each gets its own independent result; `DerivedContentComposer`'s existing overlap ordering (§2.1) places each correctly without any new dedup logic on the Contributions side |
| A contribution throws (design or defect) | `ContributionRegistry.run` catches it, records an error diagnostic with `content: nil`, and continues with the remaining contributions (§6.1, §8) |
| A contribution's result is stale (`sourceGeneration` mismatch) at splice time | Export: rejected by `DerivedContentComposer`'s existing guard (§2.1), authored text preserved. Preview: rejected by `PreviewContributionAdapter`'s equivalent guard (§6.6) before merging |
| More than 64 contribution results in one document (Preview) | Results beyond the cap are silently not merged (§11) — a defensive ceiling, not an expected real-world case |
| Export's own extra parse (§7.1) fails | Propagates as the same `ExportError.parseFailed` the *second*, `ExportComposer`-internal parse would already throw for the same malformed input — the export fails with one clear error either way, not two different ones depending on which parse noticed first |
| Text-filter command file removed/not executable between discovery and invocation | `TextFilterRunner.run` throws `.launchFailed`; alert names the command, editor untouched |
| Command exits non-zero | `.nonZeroExit(code:stderr:)`; alert shows the code and the script's own stderr (bounded, §11) if any; editor untouched |
| Command exceeds the timeout | Process terminated, `.timedOut` thrown; editor untouched |
| Caller cancels (e.g. window closed mid-run) | Process terminated, `.cancelled`/`CancellationError`; editor untouched, no alert (the user withdrew the action, not an error — mirrors `ExportCoordinator`'s existing `catch is CancellationError` handling, §2.1) |
| Command's stdout exceeds `maxOutputBytes` | Reading stops, process terminated, `.outputTooLarge` thrown; editor untouched |
| Command's stdout is not valid UTF-8 | `.outputNotDecodable` thrown; editor untouched |
| Command produces empty stdout on a zero exit | Treated as a *successful* empty replacement (deletes the selection) — a script that legitimately produces no output (e.g. a "delete matching lines" filter) is not an error; this is a deliberate, narrow product decision, not an oversight |
| No selection when a text filter is invoked | Whole document text is used as input and replaced (J4) |
| Commands folder does not exist yet | `TextFilterCommandDiscovery.discoverCommands()` creates it empty and returns `[]` — first launch after this epic ships is not an error state (J6) |

There is no failure path in this table that leaves `FileDocument.text` in
a partially-mutated state — every text-filter failure is caught *before*
any editor mutation is attempted (§4 rule 6), and every contribution
failure is caught before it can affect anything beyond its own,
independent placement decision (§4 rule 2).

## 10. Security and trust boundary

**First-party contributions are fully trusted, in-process Swift** — the
same trust level as the rest of the app's own code. "Isolation" for this
half of the epic (§2.2) means fault/result isolation (§6.1, §8), not OS
sandboxing; there is no untrusted input to a contribution beyond the
document text itself, which the rest of the app already treats as trusted
local content the user is editing.

**Text-filter commands are the first subprocess launch in this codebase**
and the part of this epic where "trust boundary" means something real.
This design's obligations, matching `RELEASE_HARDENING.md` §3's baseline
exactly:

- **Structured launch, never shell interpolation** — `Process.executableURL`
  is set directly to the discovered script's `URL`; `Process.arguments`
  is always `[]` in this epic's scope (no per-invocation arguments are
  passed — input travels only via stdin, §7.2); no string is ever built by
  concatenating document text, a file path, or any other input and handed
  to `/bin/sh -c` or equivalent.
- **Explicit working directory** — the active document's own containing
  folder when it has one (`fileURL.deletingLastPathComponent()`), else the
  user's home directory for an untitled document. Never the app's own
  bundle directory, and never "whatever the app process's own cwd happens
  to be" (the exact "accidentally inheriting unrestricted process state"
  the issue names).
- **Documented, bounded environment** — a fixed, small set:
  `PATH` (a hard-coded minimal value, not inherited from the app's own
  process environment), `HOME`, `TMPDIR`, `MACDOWN_DOCUMENT_PATH` (the
  saved file's path, unset for an untitled document), and
  `MACDOWN_SELECTION_LENGTH` (character count of the piped input). No
  other variable from the app's own process environment is passed
  through.
- **Bounded execution time with cancellation** — `Limits.standard.timeout`
  (10s default) via the watchdog pattern in §8; termination on both
  timeout and caller cancellation.
- **Bounded stdout/stderr** — `Limits.standard.maxOutputBytes` (4 MB
  default, §11); reading stops and the process is terminated if exceeded.
- **Cannot hang the main actor** — §4 rule 4, §8.
- **Any failure preserves the original text and surfaces a useful error**
  — §9's table, in full.
- **Replacement is one explicit, undoable editor mutation, only after
  success** — §7.2, reusing the existing `applyAssistOutcome` idiom
  (§2.1).
- **User-installed commands are visibly distinguished from built-in
  functionality** — the Commands menu and palette both label discovered
  scripts under a "Commands" heading distinct from any app command row;
  nothing in this epic presents a user's own script as first-party
  MacDown 2 functionality.

**What this design does *not* claim.** Once launched, a text-filter script
runs with the same OS-level privileges as any process the user could start
from Terminal — full filesystem access, full network access, no sandbox.
This is consistent with D7 (unsandboxed, direct distribution) and with the
issue's own scope ("a simple local text-filter command system," not a
hardened multi-tenant sandbox). MacDown 2's safety obligation is narrower
and is fully enumerated above: launch safely, bound what it waits for, and
never corrupt the document — not "safely execute untrusted code." A user
who places a malicious script in their own Commands folder has already
made a decision equivalent to running that script directly; this epic does
not attempt to protect against that, and no acceptance criterion in issue
#15 asks it to.

**The rendered-fragment HTML this epic introduces stays local and
offline**, matching D9: `ExportService.renderMarkdownFragment` performs no
network fetch and, per §6.4, deliberately does not preserve raw HTML
passthrough — a generated fragment (a list of TOC links) has no
legitimate need for it, so this is strictly more conservative than the
main document export pipeline, which does allow raw HTML under an
explicit, existing policy (§2.1).

**The JavaScriptCore extension API (§17, Slice 8) is design-only.** No
runtime trust boundary exists for it in shipped code from this epic — the
design document itself must specify one before any future epic implements
it, and that specification is explicitly out of scope for what ships in
1.0 (issue #15's own "design only, no third-party loader in macOS 1.0").

| Export's extra, contribution-only parse (§7.1, §1 risk 2) | One additional swift-markdown parse of the same text `ExportComposer.prepare` already parses again internally moments later; E06's own parse budget already bounds a single parse, and export already tolerates file I/O, HTML rendering, and (for PDF) WebKit layout + printing costs an order of magnitude larger — one extra parse is not expected to be observable against those | Manual observation across a representative document size; no new package benchmark is justified for a cost this small relative to export's existing, larger costs |
| Preview-merged contribution result cap | 64 results per document (§6.6, §9) — a defensive ceiling far beyond any real `[TOC]` marker count, preventing a pathological document (thousands of markers) from doing unbounded merge work on every keystroke-triggered reparse | Unit test constructing more than 64 results and asserting the merge stops there |
| Text-filter execution time | `Limits.standard.timeout = 10s` (§6.5, §10) | Unit test asserting a script that sleeps past the timeout is terminated and throws `.timedOut` within a small margin of 10s |
| Text-filter output size | `Limits.standard.maxOutputBytes = 4 MB` (§6.5, §10) | Unit test asserting an oversized-output script throws `.outputTooLarge` rather than buffering unboundedly |
| Export's `contributions:` array once populated | Already bounded by `ExportResourceBudget.standard.maxDerivedFragmentCount` (4096) / `.maxAggregateDerivedHTMLBytes` (32 MB) — both already shipped by E12 and already comfortably cover a single TOC contribution per document; no new export-side budget is added by this epic (§2.1) | Existing `ExportServiceTests` budget coverage, unchanged |

Nothing in this epic touches the keystroke-to-highlight or preview-debounce
hot paths measured by earlier epics; contribution running rides on the

## 13. Export and interoperability

- The authored `[TOC]` line is exactly what round-trips through save,
  reopen, copy/paste, and source control — never rewritten (§4 rule 1).
  Only the rendered Preview/Export presentation differs from the raw
  source, exactly like every other Markdown construct already renders
  differently from its source text.
- Opening a `[TOC]`-containing document in a hypothetical future version
  that removed this contribution would show the literal, still-valid
  Markdown text `[TOC]` — a graceful, unsurprising degradation, not a
  broken document.
- TOC's generated list is plain text, not clickable links, in this epic
  (§1, §6.2, §18) — confirmed by reading `ExportService` directly, no part
  of today's export pipeline generates a stable `id` attribute for a
  heading, and cmark-gfm does not do this on its own. Claiming an anchor
  link that goes nowhere would be worse than a plain list; building a
  correct heading-id generator (and reconciling it with Preview, which —
  also confirmed by reading `TextualMarkdownPreview` directly — hands
  every link, including a same-document `#fragment` link, to
  `NSWorkspace.shared.open` today, so a TOC link would not scroll Preview
  to the heading even if it resolved) is real, separable work, named as
  follow-up scope in §18 rather than attempted speculatively here.
- A document containing a `[TOC]` marker but opened in a build where
  `Contributions` is unavailable for any reason is unreachable in
  practice (the App target always links `Contributions`), so no
  degraded-but-still-functional import path is specified beyond "the
  marker renders as plain text," which is already the pre-epic behavior
  for a document with `[TOC]` in it today.
- Text-filter commands have no export/interoperability surface of their
  own — they mutate the open document in place, through the same save
  path every other edit already uses.

## 15. Adversarial corpus

- A document with hundreds of `[TOC]` markers (exercises the 64-result cap,
  §11, and `DerivedContentComposer`'s existing overlap/ordering logic at
  volume).
- A `[TOC]` marker immediately adjacent to (same line as, or with no blank
  line around) a heading — must not be misidentified as part of that
  heading's content.
- A heading whose title contains Markdown link syntax, unescaped brackets,
  or emoji — TOC's generated link text must not break the surrounding
  list's Markdown syntax.
- A document with headings but no `[TOC]` marker, and the reverse (marker,
  no headings) — both already covered as named failure-model rows (§9).
- A text-filter script that is executable but not actually a valid
  executable (garbage bytes, wrong architecture) — must surface
  `.launchFailed`, not crash the app.
- A text-filter script that ignores stdin entirely and exits immediately —
  must not hang waiting for a stdin write the script never reads (a
  realistic pipe-buffering hazard when input exceeds the pipe's internal
  buffer and the script never drains it).
- A text-filter script that writes to stdout in a tight loop indefinitely —
  exercises both the timeout and the output-size cap, whichever is hit
  first.
- A text-filter script that forks a long-lived child process and exits
  immediately itself — `TextFilterRunner` must not wait on grandchildren
  it did not launch; only the direct child's exit/termination governs the
  result.
- Rapid, repeated invocations of the same text filter (a user mashing the
  palette's Return key) — each invocation is independent; two concurrent
  runs of the same script must not corrupt each other's output capture.
- A Commands folder containing a mix of executable scripts, non-executable
  files, and subdirectories — discovery must include only the first kind
  and skip the rest without erroring.
- An extremely long single line inside a document being scanned for `[TOC]`
  markers — the line-scan must not be quadratic in document size (reuses
  `SourceMap`'s already-linear construction, §2.1, rather than a new
  per-character scan).

## 18. Definition of Done and residual risk

An epic is complete only when `EPIC_STANDARD.md` §4's full checklist is
satisfied. For E14 specifically:

- [ ] All 11 acceptance criteria in issue #15 are demonstrated (§14 maps
      each to its evidence).
- [ ] `ContributionsTests`, `TextFiltersTests`, and the App-target adapter
      tests all pass in CI.
- [ ] SwiftFormat/SwiftLint --strict pass.
- [ ] The app and CLI build in Release configuration.
- [ ] The two named on-device journeys (palette keystroke path,
      text-filter replacement keystroke-to-undo-step path) are either
      executed on real macOS 26 hardware, or explicitly recorded as
      unverified in the release-evidence ledger — never inferred passed
      (§14).
- [ ] `planning/epics/README.md`'s E14 row is updated to reflect what
      actually shipped, including any scope narrowed during
      implementation.
- [ ] `planning/extension-api-design.md` exists and satisfies Slice 8.

**Residual risk, named rather than hidden in a PR conversation:**

1. **The `.html(ContributionRepresentation)` case is real, typed, and
   completely unhandled.** Both `PreviewContributionAdapter` and
   `ExportContributionAdapter`'s switches over `ContributionRepresentation`
   are written without a `default:` case specifically so that the day a
   contribution (E19 math, most plausibly, or E20 for a diagram engine
   that cannot round-trip through Markdown) produces `.html`, both
   adapters fail to compile until a human decides what to do. That
   decision is not a small one: **Preview's block renderer has no
   HTML-fragment rendering capability at all today** — every `PreviewBlock`,
   regardless of `BlockKind`, is fed through `PreviewMarkupParser`/Textual
   as Markdown-shaped text (confirmed by reading `PreviewBlock.swift` and
   the block-rendering view directly, not inferred). Giving Preview a real
   HTML-fragment rendering path (most plausibly a sandboxed `WKWebView`-based
   block, mirroring the isolation `PDFExportAdapter` already uses for
   export) is real, unstarted engineering work this epic explicitly does
   not attempt, and E19/E20's own architecture documents must scope it
   before either epic can ship a contribution whose result cannot be
   expressed as Markdown.
2. **TOC's list entries are plain text, not clickable links** (§3 J2, §13)
   — discovered during Slice 2 implementation, not anticipated when this
   document was first drafted: no part of today's export pipeline
   generates a stable `id` attribute for a heading, and Preview hands
   every link, anchor or not, to `NSWorkspace.shared.open` rather than
   scrolling to it. Both are real, pre-existing gaps a correct clickable
   TOC would need to close — a heading-anchor-id generator agreed between
   `Contributions` and `ExportService` (most plausibly a small addition to
   `MarkdownEngine`, which both already depend on), and, separately,
   in-preview anchor-link handling that does not exist for *any* link
   today, TOC-generated or hand-authored. Filed as follow-up rather than
   built speculatively inside this epic.
3. **Export performs one extra parse per export** (§1 risk 2, §7.1, §11) —
   accepted as proportionally negligible next to export's existing costs,
   but a real, measurable inefficiency that a future performance pass
   could remove by threading a shared parse through both `ExportCoordinator`
   and `ExportComposer`, at the cost of a new coupling between them this
   epic deliberately avoided introducing without a proven need.
4. **Text-filter commands are unsandboxed automation, not a security
   boundary against a malicious script** (§10) — an accepted, explicit
   consequence of D7 and the issue's own scope, not a gap this epic failed
   to close.
5. **The command palette's app-commands list is a small, hand-maintained
   array** (§5) that will drift out of sync with `WorkspaceCommands.swift`'s
   real command set unless a future change remembers to update both. No
   automated consistency check (mirroring `FormatRegistryConsistencyTests`,
   §2.1's registry precedent) is built for this in E14, because the
   palette's initial app-command set is intentionally small (§1) and the
   drift risk is judged acceptable at that size; a follow-up issue is
   filed if this list grows enough to justify one.
6. **Sample script coverage is minimal** (an uppercase example and
   possibly one more, §1/§9/§17 Slice 6) — enough to prove and dogfood the
   mechanism, not a curated library of useful filters. A richer example
   set is reasonable follow-up work, not required for this epic's own
   acceptance criteria.

Residual risks 1, 2, and 3 are significant enough to warrant their own
follow-up GitHub issues at the close of this epic — 1 against E19/E20's own
dependency chain, 2 and 3 as standalone polish/performance follow-ups —
rather than left implicit in this document, per `EPIC_STANDARD.md` §3.18.
